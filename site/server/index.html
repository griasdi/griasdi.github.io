Run your own server.

griasdi-server is one program for Linux. It holds your communities, stores and forwards what your members encrypt, and can’t read any of it. This guide covers installing it, setting it up, configuring it and keeping it up to date.

Server builds are coming soon. Until then, this is how it will work.

What a server does

Every griasdi community lives on a server. Run your own and your crew’s communities, messages and files live on hardware you choose. Your members connect to it from the griasdi app like to any other server.

  • It stores ciphertext. Messages, files, voice, screen sharing and the names of communities, channels and roles are encrypted on your members’ devices. What a server sees
  • No accounts, no passwords. People are keys. They join with invite links, and the first link makes you the owner.
  • It hands out updates and models. The server fetches signed app builds and on-device speech models and passes them on to the apps connected to it. Only builds signed by us are taken.
  • It serves no web page. Invite links point to griasdi.github.io/join, which hands them to the app. The server talks only to griasdi apps, other griasdi servers and our catalog of builds.

What you need

  • A Linux machine

    x86_64 or ARM64, with systemd and glibc 2.39 or newer: Ubuntu 24.04, Debian 13, Fedora 40 or later. In a container, any host that runs Podman.

  • A name or address

    The host name (or IP address) your members’ apps reach the server by, such as chat.example.org. It goes into every link the server makes.

  • Two open ports

    UDP 1337 for everything griasdi does. TCP 1337 for app updates over HTTPS, for apps that can’t reach the server over QUIC; without it the server logs a warning at start and those apps skip that fallback.

Install

Every release carries the server for x86_64 and ARM64 in three forms, next to SHA256SUMS to check them with sha256sum -c --ignore-missing SHA256SUMS. The packages and the tarball bring the systemd unit griasdi-server.service. For a container, skip to In a container.

  • griasdi-server_<version>-1_<arch>.debamd64 or arm64

    Debian and Ubuntu.

  • griasdi-server-<version>-1.<arch>.rpmx86_64 or aarch64

    Fedora and other rpm distributions.

  • griasdi-server-<version>-<arch>-linux.tar.gzx86_64 or aarch64

    Any other Linux with systemd. Installs into /usr/local.

Debian and Ubuntu

$ sudo apt install ./griasdi-server_*.deb

Fedora

$ sudo dnf install ./griasdi-server-*.rpm

Other Linux

$ sudo tar -xzf griasdi-server-*-linux.tar.gz --strip-components=1 -C /usr/local
$ sudo systemctl daemon-reload
$ sudo install -d -m755 /etc/griasdi

The service is installed but stays idle until its configuration exists.

Set it up

  1. Write the configuration

    Use the host name your members reach the server by. init refuses to overwrite a configuration that exists.

    $ sudo griasdi-server init --public-host chat.example.org --listen '[::]:1337' \
    --data-dir /var/lib/griasdi --name "$(hostname -s)" \
    --config /etc/griasdi/griasdi-server.toml
$ sudo chmod 644 /etc/griasdi/griasdi-server.toml

  2. Start the service

    $ sudo systemctl enable --now griasdi-server

    Open UDP 1337 and TCP 1337 in your firewall.

  3. Take the setup link

    At start the server prints its griasdi:server:… link and, while it has no community yet, a setup link.

    $ sudo journalctl -u griasdi-server -o cat | grep -A1 'setup link'

  4. Open it in griasdi

    Paste the setup link into Join by link in the app, or open it as the first link when griasdi starts. That creates the server’s first community and makes you the server’s admin.

The setup link works once and for 24 hours. A restart keeps it. Lost it? sudo griasdi-server setup-link --config /etc/griasdi/griasdi-server.toml prints a new one and voids the old one, for as long as the server has no community.

In a container

Every build is also the image oci.doodleshnookie.net/griasdi-server for amd64 and arm64, pulled without an account. Its tags are the update channel (dev, nightly, release) and the build number; a release adds its version and latest.

$ podman run -d --name griasdi-server --restart=always \
    -p 1337:1337/udp -p 1337:1337/tcp \
    -e GRIASDI_PUBLIC_HOST=chat.example.org -e GRIASDI_NAME="$(hostname -s)" \
    -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server:release
$ podman logs griasdi-server | grep -A1 'setup link'
  • GRIASDI_PUBLIC_HOSTrequired

    The host name or address your members reach the server at.

  • GRIASDI_NAMEdefault griasdi

    The server’s display name.

Both are read on the first start only, when the server writes griasdi-server.toml into the volume, with the image’s channel in [updates]. The volume holds the data, the configuration and the server’s binaries. The server updates itself inside the volume, so an updated server survives a restart of its container, and a newer image only matters for a new volume.

Keep --restart=always: when the server can’t replace itself in place after an update, it exits to be started again into the new build.

Communities and admins

  • The community the setup link creates belongs to the server and can’t be dissolved. A server that had communities before makes its oldest one this community.
  • Everyone else joins with invite links, made in the app. Each lets one person in and expires after 1 hour to 30 days, 7 by default. Whoever manages a community can also make its public link, for 10, 20, 50, 100 or any number of people; it never expires and works until it is used up or turned off.
  • By default anyone on the server may create communities, at most 20 each. community_creation = "admins" leaves that to the admins.
  • Whoever redeemed the setup link is an admin; admins in the configuration adds more by user id. An admin finds Settings › Servers › Manage next to the server: version and uptime, users, devices and who is online, live voice, calls, shares and transfers, stored files and messages, and every community with its counts. Communities are named only where the admin is a member. Never any content.

Configuration

/etc/griasdi/griasdi-server.toml, written by init. The first four keys come from its options; everything else has a default. The file may hold only these keys: an unknown or misspelled key is an error and the server doesn’t start. Restart the service after a change.

Written by initgriasdi-server.toml
name = "chat"
listen = "[::]:1337"
public_host = "chat.example.org"
data_dir = "/var/lib/griasdi"

Server

  • name--name

    The server’s display name.

  • listen--listen, default 0.0.0.0:1337

    The UDP address to listen on. The server also takes the same TCP port for update downloads.

  • public_host--public-host

    The host name or address clients reach the server by.

  • data_dir--data-dir

    The database, the stored files and the server’s TLS identity.

  • community_creationdefault "anyone"

    Who may create communities: "anyone" or "admins".

  • adminsdefault []

    User ids in hex with server-admin rights, besides whoever redeemed the setup link.

Files

  • max_blob_bytesdefault 26214400, 25 MiB

    The largest attachment the server stores. 25 MiB is also the most: every app treats it as its ceiling, and a larger value is refused at load. A bigger file isn’t stored at all; the app sends it member to member instead, through the server.

  • blob_ttl_daysdefault [1, 7, 30]

    The lifetimes in days a sender may pick for an attachment. Values outside 1 to 3650 are dropped; an empty list is an error. The longest is the most the server keeps any file.

  • blob_ttl_default_daysdefault 30

    The lifetime the app preselects. One that isn’t in blob_ttl_days falls back to the largest entry below it, else the smallest.

  • max_blob_bytes_per_userdefault 1073741824, 1 GiB

    Stored bytes one user may hold; 0 turns the quota off. A user at the quota sends files member to member.

  • max_hosted_bytesdefault 8589934592, 8 GiB

    The largest file the server relays between members; 0 turns relaying off.

Rate limit

  • rate_burstdefault 60

    Requests one device may send at once: posting messages, creating groups and calls, joining voice, sharing and the like.

  • rate_per_secdefault 10

    How fast that allowance refills, per second. A device over the limit is told “rate limited” until it has refilled.

Updates and august

  • [updates] channeldefault "dev"

    The channel the server updates itself from: "dev", "nightly" or "release".

  • [august] enableddefault true

    false cuts the server off from august, our catalog of builds and models. It then fetches no app builds and no speech models for its members and forwards no performance reports.

  • [august] host, port, fingerprint

    Where august is and the SHA-256 fingerprint of its key (64 hex digits). The defaults are ours; leave them out.

Optional tablesgriasdi-server.toml
[updates]
channel = "release"

[august]
enabled = true

Updates

Your server

From a package or the tarball, the server doesn’t update itself; it logs that and leaves it to you. Install the next release over it the way you installed the first.

In the container, the server updates itself from its channel: it fetches a new build, checks its signature against the keys compiled into it, installs it in the volume and hands its socket over to the new build. Apps reconnect at once. It only ever moves to a newer build. A build that won’t start, or dies three times right after its start, is set aside, and the previous one runs again.

Before it changes its database schema the server keeps a copy, griasdi.db.pre-v<old version>, next to the database.

Your members’ apps

The server follows august, our catalog, and fetches every signed app build and speech model in 1 MiB pieces, from august and from other servers at once. It trusts neither: each piece is checked against the signed manifest, and an older build is never taken. Once it holds a build of the apps’ channel it announces it to them, and they fetch it from all the servers that have it.

Voice sessions live in memory only. After a restart the apps in a call join it again on their own.

Files and commands

Where things live

  • /etc/griasdi/

    The configuration. Root’s; the service only reads it.

  • /var/lib/griasdi/

    The database, stored files and TLS identity. The service runs as a user systemd allocates, and only root reads this directory, so use sudo.

  • …/storage/

    The caches of update builds and model files, refilled from august if lost. A directory of its own, so you can mount bulk storage there and keep the databases on the local disk.

Commands

Each takes --config <path>, default griasdi-server.toml in the current directory.

  • run

    Runs the server. The systemd unit does this.

  • init

    Writes a new configuration from --public-host, --listen, --data-dir and --name; refuses to overwrite.

  • setup-link

    Prints a new setup link and voids the old one, while the server has no community.

  • update

    Lists the update builds stored on this host: each channel’s newest and the builds kept.

  • --version

    The version, with build number, channel and commit once the build is known.

Logs: sudo journalctl -u griasdi-server.
