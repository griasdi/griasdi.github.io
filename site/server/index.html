Run your own server.

griasdi-server is one program for Linux. It holds your communities, stores and forwards what your members encrypt, and can’t read any of it. This guide covers installing it, setting it up, its license, configuring it and keeping it up to date.

Server builds are coming soon. Until then, this is how it will work.

What a server does

Every griasdi community lives on a server. Run your own and your crew’s communities, messages and files live on hardware you choose. Your members connect to it from the griasdi app like to any other server.

  • It stores ciphertext. Messages, files, voice, screen sharing and the names of communities, channels and roles are encrypted on your members’ devices. What a server sees
  • No accounts, no passwords. People are keys. They join with invite links, and the first link makes you the owner.
  • It hands out updates and models. The server fetches signed app builds and on-device speech models and passes them on to the apps connected to it. Only builds signed by us are taken.
  • It serves no web page. Invite links point to griasdi.github.io/join, which hands them to the app. The server talks only to griasdi apps, other griasdi servers and our catalog of builds.

What you need

  • A Linux machine

    x86_64 or ARM64 with systemd: Ubuntu 24.04, Debian 13, Fedora 40 or later. In a container, any host that runs Docker or Podman.

  • System packages

    Only glibc 2.39 or newer and libgcc_s, which those distributions bring. The server carries its own SQLite and TLS: no OpenSSL, no database server. The image brings everything it needs.

  • A name or address

    The host name (or IP address) your members’ apps reach the server by, such as chat.example.org. It goes into every link the server makes.

  • Two open ports

    UDP 1337 for everything griasdi does. TCP 1337 for app updates over HTTPS, for apps that can’t reach the server over QUIC; without it the server logs a warning at start and those apps skip that fallback. Outgoing, it reaches august on UDP 1328, and on TCP 1328 over HTTPS when that doesn’t get through.

Install

Every release carries the server for x86_64 and ARM64 in three forms, next to SHA256SUMS to check them with sha256sum -c --ignore-missing SHA256SUMS. The packages and the tarball bring the systemd unit griasdi-server.service. For a container, skip to In a container.

Debian and Ubuntu

Download griasdi-server_<version>-1_<arch>.deb, for amd64 or arm64, and install it:

$ sudo apt install ./griasdi-server_*.deb

Fedora

For Fedora and other rpm distributions, download griasdi-server-<version>-1.<arch>.rpm, for x86_64 or aarch64, and install it:

$ sudo dnf install ./griasdi-server-*.rpm

Other Linux

For any other Linux with systemd, download griasdi-server-<version>-<arch>-linux.tar.gz, for x86_64 or aarch64, and unpack it into /usr/local:

$ sudo tar -xzf griasdi-server-*-linux.tar.gz --strip-components=1 -C /usr/local
$ sudo systemctl daemon-reload
$ sudo install -d -m755 /etc/griasdi

The service is installed but stays idle until its configuration exists.

Set it up

  1. Write the configuration

    Use the host name your members reach the server by. init refuses to overwrite a configuration that exists.

    $ sudo griasdi-server init --public-host chat.example.org --listen '[::]:1337' \
    --data-dir /var/lib/griasdi --name "$(hostname -s)" \
    --config /etc/griasdi/griasdi-server.toml
$ sudo chmod 644 /etc/griasdi/griasdi-server.toml

  2. Start the service

    $ sudo systemctl enable --now griasdi-server

    Open UDP 1337 and TCP 1337 in your firewall.

  3. Take the setup link

    At start the server prints its griasdi:server:… link and, while it has no community yet, a setup link.

    $ sudo journalctl -u griasdi-server -o cat | grep -A1 'setup link'

  4. Open it in griasdi

    Paste the setup link into Join by link in the app, or open it as the first link when griasdi starts. That creates the server’s first community and makes you the server’s admin.

  5. Get the free license

    In Settings › Servers › Manage, Get free license raises the server from 10 members and 1 community to 32 members and 3. See License.

The setup link works once and for 24 hours. A restart keeps it. Lost it? sudo griasdi-server setup-link --config /etc/griasdi/griasdi-server.toml prints a new one and voids the old one, for as long as the server has no community.

In a container

Every build is also the image oci.doodleshnookie.net/griasdi-server for amd64 and arm64, pulled without an account. Its tags are the update channel (dev, nightly, release) and the build number; a release adds its version and latest.

Docker

$ docker run -d --name griasdi-server --restart=always \
    -p 1337:1337/udp -p 1337:1337/tcp \
    -e GRIASDI_PUBLIC_HOST=chat.example.org -e GRIASDI_NAME="$(hostname -s)" \
    -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server:release
$ docker logs griasdi-server | grep -A1 'setup link'

Docker Compose

In a directory of its owncompose.yaml
services:
  griasdi-server:
    image: oci.doodleshnookie.net/griasdi-server:release
    restart: always
    ports:
      - "1337:1337/udp"
      - "1337:1337/tcp"
    environment:
      GRIASDI_PUBLIC_HOST: chat.example.org
      GRIASDI_NAME: chat
    volumes:
      - griasdi:/var/lib/griasdi

volumes:
  griasdi:
$ docker compose up -d
$ docker compose logs --no-log-prefix griasdi-server | grep -A1 'setup link'

Podman

$ podman run -d --name griasdi-server --restart=always \
    -p 1337:1337/udp -p 1337:1337/tcp \
    -e GRIASDI_PUBLIC_HOST=chat.example.org -e GRIASDI_NAME="$(hostname -s)" \
    -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server:release
$ podman logs griasdi-server | grep -A1 'setup link'
  • GRIASDI_PUBLIC_HOSTrequired

    The host name or address your members reach the server at.

  • GRIASDI_NAMEdefault griasdi

    The server’s display name.

Both are read on the first start only, when the server writes griasdi-server.toml into the volume, with the image’s channel in [updates] unless it is dev, the default. The volume holds the data, the configuration and the server’s binaries. The server updates itself inside the volume, so an updated server survives a restart of its container, and a newer image only matters for a new volume.

Keep --restart=always (restart: always in Compose): when the server can’t replace itself in place after an update, it exits to be started again into the new build.

Communities and admins

  • The community the setup link creates belongs to the server and can’t be dissolved. A server that had communities before makes its oldest one this community.
  • Everyone else joins with invite links, made in the app. Each lets one person in and expires after 1 hour to 30 days, 7 by default. Whoever manages a community can also make its public link, for 10, 20, 50, 100 or any number of people; it never expires and works until it is used up or turned off.
  • By default anyone on the server may create communities, at most 20 each and as many as its license allows. community_creation = "admins" leaves that to the admins.
  • Whoever redeemed the setup link is an admin; admins in the configuration adds more by user id. An admin finds Settings › Servers › Manage next to the server: version and uptime, users, devices and who is online, live voice, calls, shares and transfers, stored files and messages, its license, and every community with its counts. Communities are named only where the admin is a member. Never any content.

License

A server without a license lets in 10 members and 1 community. The free license raises that to 32 members and 3 communities, for one click in the app.

LicenseMembersCommunitiesHow
None101Where every server starts.
Free323Get free license in the app, for the server’s admins.

What counts

  • Members are the distinct people across all of the server’s communities, bots included. Someone already on the server joins its other communities even when it is full.
  • Past the limits a newcomer is told “This server is full”, and another community is refused with “This server allows only 1 community”, for admins too. The community the setup link creates always fits.
  • Nothing is taken away: a server over its limits keeps every member and community and only stops growing.

In the app

An admin finds the License section in Settings › Servers › Manage: its status, members and communities against the limits, and the Server ID. Get free license shows while no license is in effect and the server uses august, which issues it. Copy license link and Save license file… keep a copy, for example to install it again after you set the server up anew.

How long it holds

  • A license names the server by the fingerprint of its key, the Server ID. It works on that server only, so it is no secret.
  • It runs for a year, and august renews it while the server reaches august. A server that hasn’t reached august for a year falls back to 10 members and 1 community. With [august] enabled = false there is no free license and no renewal.

Install a license

A license is a griasdi:license:… link or a .griasdi-license file holding one. In the app, open it with Add license… in the License section or paste the link into Join by link. On the host, license takes the link or the file:

$ sudo griasdi-server license chat.griasdi-license --config /etc/griasdi/griasdi-server.toml
installed: 32 members, 3 communities, valid until 2027-11-09 (UTC)

A running server uses it at once, without a restart. In a container, hand it the link; "$(cat …)" reads it from the file:

Docker

$ docker exec griasdi-server /var/lib/griasdi/bin/current license \
    "$(cat chat.griasdi-license)" --config /var/lib/griasdi/griasdi-server.toml

Docker Compose

# in the directory of compose.yaml
$ docker compose exec griasdi-server /var/lib/griasdi/bin/current license \
    "$(cat chat.griasdi-license)" --config /var/lib/griasdi/griasdi-server.toml

Podman

$ podman exec griasdi-server /var/lib/griasdi/bin/current license \
    "$(cat chat.griasdi-license)" --config /var/lib/griasdi/griasdi-server.toml

Configuration

/etc/griasdi/griasdi-server.toml, written by init. The first four keys come from its options; everything else has a default. The file may hold only these keys: an unknown or misspelled key is an error and the server doesn’t start. Restart the service after a change.

Written by initgriasdi-server.toml
name = "chat"
listen = "[::]:1337"
public_host = "chat.example.org"
data_dir = "/var/lib/griasdi"

Server

  • name--name

    The server’s display name.

  • listen--listen, default 0.0.0.0:1337

    The UDP address to listen on. The server also takes the same TCP port for update downloads.

  • public_host--public-host

    The host name or address clients reach the server by.

  • data_dir--data-dir

    The database, the stored files and the server’s TLS identity.

  • community_creationdefault "anyone"

    Who may create communities: "anyone" or "admins".

  • adminsdefault []

    User ids in hex with server-admin rights, besides whoever redeemed the setup link.

Files

  • max_blob_bytesdefault 26214400, 25 MiB

    The largest attachment the server stores. 25 MiB is also the most: every app treats it as its ceiling, and a larger value is refused at load. A bigger file isn’t stored at all; the app sends it member to member instead, through the server.

  • blob_ttl_daysdefault [1, 7, 30]

    The lifetimes in days a sender may pick for an attachment. Values outside 1 to 3650 are dropped; an empty list is an error. The longest is the most the server keeps any file.

  • blob_ttl_default_daysdefault 30

    The lifetime the app preselects. One that isn’t in blob_ttl_days falls back to the largest entry below it, else the smallest.

  • max_blob_bytes_per_userdefault 1073741824, 1 GiB

    Stored bytes one user may hold; 0 turns the quota off. A user at the quota sends files member to member.

  • max_hosted_bytesdefault 8589934592, 8 GiB

    The largest file the server relays between members; 0 turns relaying off.

Rate limit

  • rate_burstdefault 60

    Requests one device may send at once: posting messages, creating groups and calls, joining voice, sharing and the like.

  • rate_per_secdefault 10

    How fast that allowance refills, per second. A device over the limit is told “rate limited” until it has refilled.

Updates and august

  • [updates] channeldefault "dev"

    The channel the server updates itself from: "dev", "nightly" or "release".

  • [august] enableddefault true

    false cuts the server off from august, our catalog of builds and models. It then fetches no app builds and no speech models for its members, forwards no performance reports, gets no free license and no renewal of its license.

  • [august] host, port, fingerprint

    Where august is and the SHA-256 fingerprint of its key (64 hex digits). The defaults are ours; leave them out.

Optional tablesgriasdi-server.toml
[updates]
channel = "release"

[august]
enabled = true

Updates

Your server

From a package or the tarball, the server doesn’t update itself. Once a newer build is out it logs that and tells its admins in the app’s notification center, with what to do. Install the next release over it the way you installed the first.

In the container, the server updates itself from its channel: it fetches a new build, checks its signature against the keys compiled into it, installs it in the volume and hands its socket over to the new build. Apps reconnect at once. It only ever moves to a newer build. A failed install is tried again after 15 minutes, then after twice the wait each time, up to 6 hours. A build that won’t start, or dies three times right after its start, is set aside, and the previous one runs again. If the server still runs an older build an hour after a newer one came out, or has had no contact with august for 6 hours, its log and its admins’ notification center say why and what to do.

Before it changes its database schema the server keeps a copy, griasdi.db.pre-v<old version>, next to the database.

Your members’ apps

The server follows august, our catalog, and fetches every signed app build and speech model in 1 MiB pieces, from august and from other servers at once. A file they can’t deliver comes whole from august over HTTPS on TCP 1328, and while the server has had no link to august for 30 minutes, it asks august there for new builds every 15 minutes. It trusts none of them: everything is checked against the signed manifest, and an older build is never taken. Once it holds a build of the apps’ channel it announces it to them, and they fetch it from all the servers that have it.

Voice sessions live in memory only. After a restart the apps in a call join it again on their own.

Files and commands

Where things live

  • /etc/griasdi/

    The configuration. Root’s; the service only reads it.

  • /var/lib/griasdi/

    The database, stored files and TLS identity. The service runs as a user systemd allocates, and only root reads this directory, so use sudo.

  • …/storage/

    The caches of update builds and model files, refilled from august if lost. A directory of its own, so you can mount bulk storage there and keep the databases on the local disk.

Commands

Each takes --config <path>, default griasdi-server.toml in the current directory.

  • run

    Runs the server. The systemd unit does this.

  • init

    Writes a new configuration from --public-host, --listen, --data-dir and --name; refuses to overwrite.

  • setup-link

    Prints a new setup link and voids the old one, while the server has no community.

  • license

    Installs a license from a griasdi:license: link or a license file. A running server uses it at once.

  • --version

    The version, with build number, channel and commit once the build is known.

Logs: sudo journalctl -u griasdi-server.
