Run your own server.

griasdi-server is one program for Linux. It holds your communities, stores and forwards what your members encrypt, and can’t read any of it. This guide covers installing it, setting it up, its license, configuring it and keeping it up to date.

What a server does

Every griasdi community lives on a server. Run your own and your crew’s communities, messages and files live on hardware you choose. Your members connect to it from the griasdi app like to any other server.

  • It stores ciphertext. Messages, files, voice, screen sharing and the names of communities, channels and roles are encrypted on your members’ devices. What a server sees
  • No accounts, no passwords. People are keys. They join with invite links; the setup link makes you the server’s admin and the owner of its first community.
  • It hands out updates and models. Your members’ apps get their updates and speech models from it. The server fetches signed builds and passes them on; only builds signed by us are taken. See Updates.

What you need

  • A Linux machine

    x86_64 or ARM64: Ubuntu 24.04 or newer, Debian 13, Fedora 40 or newer, or any Linux that runs containers (Docker, Podman or another OCI runtime).

    CPU and memory hardly matter: our own server runs in about 150 MB of memory on two ARM cores. Bandwidth matters more, because your members’ apps download their updates from the server. Disk: about 4 GB for the cache of app builds and speech models, plus what members store: attachments, up to 1 GiB per person by default.

  • A name or address

    The name or IP address your members’ apps reach the server by, such as chat.example.org. It goes into every invite link. A DNS name beats an IP address because it survives a move to another machine. It needs no subdomain of its own: the server keeps to its own port, so it can share a machine and its name with a website or anything else.

  • Port 1337, UDP and TCP

    Open it for both, and forward it if the machine sits behind a router. Outgoing connections need no rule on most networks; Updates names them.

Install and set up

Pick how you run it; everything below the choice is for that way.

Ubuntu / Debian

Ubuntu 24.04 or newer and Debian 13, on x86_64 or ARM64.

  1. Install it

    $ curl -fLO https://griasdi.doodleshnookie.net/updates/latest/griasdi-server_$(dpkg --print-architecture).deb
$ sudo apt install ./griasdi-server_*.deb

    It brings the service griasdi-server, which waits until the server is set up.

  2. Set it up

    $ sudo griasdi-server init

    It asks for the name or address your members reach the server by and a name for the server, and writes /etc/griasdi/griasdi-server.toml.

  3. Start it

    $ sudo systemctl enable --now griasdi-server

    It starts now and with every boot, and comes back by itself after a crash or its own update. If ufw is active: sudo ufw allow 1337. Open port 1337 for UDP and TCP in any firewall in front of the machine too.

  4. Take the setup link

    $ sudo journalctl -u griasdi-server -o cat | grep -A1 'setup link'

    Lost it, or older than 24 hours? sudo griasdi-server setup-link prints a new one. Then open it in griasdi: see Join your server.

Day to day

  • Logs

    sudo journalctl -u griasdi-server -f

  • Configuration

    sudoedit /etc/griasdi/griasdi-server.toml, then sudo systemctl restart griasdi-server. See Configuration.

  • Commands

    sudo griasdi-server <command>, see Commands.

  • Files

    /etc/griasdi/: the configuration.

    /var/lib/griasdi/: the database, attachments, the server’s identity and its installed builds (bin/).

    /var/cache/griasdi/: the cache of app builds and models, refilled if lost. Mount bulk storage there.

Docker

Any Linux with Docker. Run the commands as root or as a member of the docker group.

  1. Set it up

    $ docker run --rm -it -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server init

    This pulls the image and asks for the name or address your members reach the server by and a name for the server. The volume griasdi keeps the configuration, the data and the server’s own updates.

  2. Start it

    $ docker run -d --name griasdi-server --restart=always \
    -p 1337:1337/udp -p 1337:1337/tcp \
    -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server

    --restart=always brings it back after a crash, after its own updates and after a reboot, as long as Docker starts at boot (sudo systemctl enable docker). Open port 1337 for UDP and TCP in any firewall in front of the machine.

  3. Take the setup link

    $ docker logs griasdi-server | grep -A1 'setup link'

    Lost it, or older than 24 hours? docker exec griasdi-server griasdi-server setup-link prints a new one. Then open it in griasdi: see Join your server.

    docker logs -f griasdi-server

  • Configuration

  • Commands

    docker exec griasdi-server griasdi-server <command>, see Commands.

  • Files

    Everything is in the volume griasdi: the configuration, the database, attachments, the server’s identity, its installed builds and the cache of app builds and models.

Podman

Podman 4.4 or newer: Ubuntu 24.04, Debian 13, Fedora. Podman runs the server as a systemd service through a Quadlet file.

  1. Set it up

    $ sudo podman run --rm -it -v griasdi:/var/lib/griasdi oci.doodleshnookie.net/griasdi-server init

    This pulls the image and asks for the name or address your members reach the server by and a name for the server. The volume griasdi keeps the configuration, the data and the server’s own updates.

  2. Describe the service

    As root/etc/containers/systemd/griasdi-server.container
    [Unit]
Description=griasdi server

[Container]
Image=oci.doodleshnookie.net/griasdi-server
ContainerName=griasdi-server
Volume=griasdi:/var/lib/griasdi
PublishPort=1337:1337/udp
PublishPort=1337:1337/tcp

[Service]
Restart=always

[Install]
WantedBy=multi-user.target

  3. Start it

    $ sudo systemctl daemon-reload
$ sudo systemctl start griasdi-server

    Podman makes the service griasdi-server from the file; it starts with every boot and comes back by itself. Open port 1337 for UDP and TCP in any firewall in front of the machine.

  4. Take the setup link

    Lost it, or older than 24 hours? sudo podman exec griasdi-server griasdi-server setup-link prints a new one. Then open it in griasdi: see Join your server.

Where it lives

  • /usr/local/bin/griasdi-server only starts the server. At every start it installs its own build into /var/lib/griasdi/bin/ when that is newer than what is there, and runs bin/current. Updates land in bin/ as well, with bin/previous kept to fall back to. Never replace files in bin/ by hand; unpacking a newer tarball moves the server forward the same way, never back.
  • Both follow data_dir in the configuration, /var/lib/griasdi. The service runs as a user systemd allocates and gives it exactly that directory, with bin/ the only place it may run programs from: keep data_dir where init puts it.
  • The cache of app builds and models (about 4 GB, refilled if lost) is /var/cache/griasdi/: mount bulk storage there to keep it off the system disk.

Join your server

  1. Open the setup link

    Paste it into Join by link in griasdi, or open it as the first link when griasdi starts. It creates the server’s first community; you become its owner and the server’s admin. See Communities and admins.

  2. Get the free license

    In Settings › Servers › Manage, Get free license raises the server from 10 members and 1 community to 32 members and 3. See License.

  3. Invite your crew

    Make invite links in the community with Invite people › Create link, one for each person, and send them.

The setup link works once and for 24 hours. A restart keeps it. A lost or expired one is replaced by the setup-link command of your install, which voids the old one, for as long as the server has no community.

Communities and admins

  • Server admins

    They run the server, not its communities. Settings › Servers › Manage shows them version and uptime, users, devices and who is online, live voice, calls, shares and transfers, stored files and messages, the license, and every community with its counts, named only where the admin is a member. Never any content. They get and install licenses, and with community_creation = "admins" only they create communities.

    Whoever redeemed the setup link is one; admins in the configuration adds more by user id, which the app shows in Settings › Account › Devices and keys. Being a server admin gives no say inside a community.

  • Owners

    They run a community: whoever creates it, and for the first community whoever redeemed the setup link. Owners can make other members owners. Every new community starts with the roles Admin (every right) and Moderator (kick, mute, mention everyone), which its owners hand out, change or delete. A community’s Admin role is not a server admin.

  • The first community belongs to the server and can’t be dissolved. A server that had communities before makes its oldest one that community.
  • Any member can make invite links, unless the owners take that right away. Each lets one person in and expires after 1 hour to 30 days, 7 by default. Members who may manage the community can also make its public link, for 10, 20, 50, 100 or any number of people; it never expires and works until it is used up or turned off.
  • By default anyone on the server may create communities, at most 20 each (server admins without that cap) and as many as the license allows.

License

A server without a license lets in 10 members and 1 community. The free license raises that to 32 members and 3 communities, for one click in the app.

LicenseMembersCommunitiesHow
None101Where every server starts.
Free323A server admin clicks Get free license in the app.

What counts

  • Members are people, counted once however many of the server’s communities they are in. Bots count like people.
  • On a full server a newcomer’s invite is refused with “This server is full. Its admin can raise the limit.” Someone already on the server can still join its other communities: they are counted already.
  • A community past the limit is refused with “This server allows only 1 community.”, for server admins too. The first community always fits.
  • Nothing is taken away: a server over its limits keeps every member and community and only stops growing.

In the app

A server admin finds the License section in Settings › Servers › Manage: its status, members and communities against the limits, and the Server ID. Get free license shows while no license is in effect and the server uses august, which issues it. Copy license link and Save license file… keep a copy, for example to install it again after you set the server up anew.

How long it holds

  • A license names the server by the fingerprint of its key, the Server ID. It works on that server only, so it is no secret.
  • It runs for a year, and august renews it while the server reaches august. A server that hasn’t reached august for a year falls back to 10 members and 1 community. With [august] enabled = false there is no free license and no renewal.

Install a license

A license is a griasdi:license:… link or a .griasdi-license file holding one. In the app, open it with Add license… in the License section or paste the link into Join by link. On the host, license takes the link or the file:

$ sudo griasdi-server license chat.griasdi-license
installed: 32 members, 3 communities, valid until 2027-11-09 (UTC)

A running server uses it at once. In a container, hand it the link, here with Docker; with Podman or Compose, take the Commands form from Day to day of your install:

$ docker exec griasdi-server griasdi-server license "$(cat chat.griasdi-license)"

Configuration

griasdi-server.toml, written by init: in /etc/griasdi/ with a package or the tarball, in the volume with a container. Change it as in Day to day of your install, then restart. init writes every key below except the [august] table: name and public_host from its questions, listen and data_dir for your install, the rest with their defaults. The file may hold only these keys: an unknown or misspelled key is an error and the server doesn’t start.

The first lines init writesgriasdi-server.toml
name = "chat"
listen = "[::]:1337"
public_host = "chat.example.org"
data_dir = "/var/lib/griasdi"

Server

  • nameasked by init

    The server’s display name.

  • listenset by init: [::]:1337 (0.0.0.0:1337 in a container)

    The address to listen on, for UDP and TCP on the same port.

  • public_hostasked by init

    The name or address your members’ apps reach the server by.

  • data_dirset by init

    The database, the stored files, the server’s TLS identity and its installed builds.

  • community_creationdefault "anyone"

    Who may create communities: "anyone" or "admins".

  • adminsdefault []

    User ids in hex with server-admin rights, besides whoever redeemed the setup link. The app shows your user id in Settings › Account › Devices and keys.

Files

  • max_blob_bytesdefault 26214400, 25 MiB

    The largest attachment the server stores. 25 MiB is also the most: every app treats it as its ceiling, and a larger value is refused at load. A bigger file isn’t stored at all; the app sends it member to member instead, through the server.

  • blob_ttl_daysdefault [1, 7, 30]

    The lifetimes in days a sender may pick for an attachment. Values outside 1 to 3650 are dropped; an empty list is an error. The longest is the most the server keeps any file.

  • blob_ttl_default_daysdefault 30

    The lifetime the app preselects. One that isn’t in blob_ttl_days falls back to the largest entry below it, else the smallest.

  • max_blob_bytes_per_userdefault 1073741824, 1 GiB

    Stored bytes one user may hold; 0 turns the quota off. A user at the quota sends files member to member.

  • max_hosted_bytesdefault 8589934592, 8 GiB

    The largest file the server relays between members; 0 turns relaying off.

Rate limit

  • rate_burstdefault 60

    Requests one device may send at once: posting messages, creating groups and calls, joining voice, sharing and the like.

  • rate_per_secdefault 10

    How fast that allowance refills, per second. A device over the limit is told “rate limited” until it has refilled.

august

  • [august] enableddefault true

    false cuts the server off from august, our catalog of builds and models. It then fetches no app builds and no speech models for its members, forwards no performance reports, gets no free license and no renewal of its license.

  • [august] host, port, fingerprint

    Where august is and the SHA-256 fingerprint of its key (64 hex digits). The defaults are ours; leave them out.

Optional tablesgriasdi-server.toml
[august]
enabled = true

Updates

Your server

Every install updates itself, whichever way you installed it. The server installs each build into bin/ in its data directory (/var/lib/griasdi/bin/, in a container inside the volume) and runs from there. It fetches each new build, checks its signature against the keys compiled into it, installs it next to the old one and hands its socket over to the new build; apps reconnect at once. It only ever moves forward, and a newer package or image moves it forward too. A failed install is tried again after 15 minutes, then after twice the wait each time, up to 6 hours. A build that won’t start, or dies three times right after its start, is set aside, and the previous one runs again. If the server still runs an older build an hour after a newer one came out, or has had no contact with august for 6 hours, its log and its admins’ notification center say why and what to do.

Before it changes its database schema the server keeps a copy, griasdi.db.pre-v<old version>, next to the database. Voice sessions live in memory only: after a restart the apps in a call join it again on their own.

What it needs: outgoing connections only. To august, our catalog of signed builds, at griasdi.doodleshnookie.net on port 1328 (UDP, and TCP as a fallback), and to other griasdi servers on their port 1337 (UDP).

It fetches new builds and models in 1 MiB pieces from august and other servers at once, like a torrent, and checks every piece against the signed manifest: it trusts neither august nor the other servers, only the signature. A file that won’t come that way comes whole from august over HTTPS. While it can’t reach august over UDP for 30 minutes, it asks there over HTTPS every 15 minutes.

Your members’ apps

The apps get their updates from the servers they are connected to. Each server announces a new build once it holds all of it, and the app takes the changed files from all announcing servers at once. If that doesn’t get through, it takes them over HTTPS from the same servers (TCP 1337), then from august. An app with no server online for 2 minutes asks august directly, and at start it checks august for up to 3 seconds.

Your server is what delivers them. It keeps the app builds for Linux, Windows and macOS and the speech models, about 4 GB, and hands them to your members’ apps. A new build moves only changed files, mostly the app program of about 170 MB, once per member and new build; builds come out up to once a day. A speech model, 0.4 to 2 GB, moves once to each member who uses it. Members connected to several servers share that load among them.

Commands

Run them as in Day to day of your install; on a package or tarball install with sudo.

  • run

    Runs the server. The service does this.

  • init

    Asks for the address and name and writes a new configuration; refuses to overwrite one. --public-host and --name answer the questions without asking.

  • setup-link

    Prints a new setup link and voids the old one, while the server has no community.

  • license

    Installs a license from a griasdi:license: link or a license file. A running server uses it at once.

  • --version

    The version, with build number, channel and commit once the build is known.
